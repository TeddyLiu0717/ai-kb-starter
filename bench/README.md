# kb.py doctor 规模基准（可复现）

> 本目录是公开内容《4000 页知识库，0.78 秒查出 720 个问题：给 AI 知识库加一道结构体检》
> （Trae 社区 Vol.02）的事实来源。
> 语料**完全合成**，不含任何真实业务内容；脚本零第三方依赖，仅用 Python 标准库。

## 复现结果（确定性 vs 机器相关）

请先分清两类数字，它们的稳定性完全不同：

| 类别 | 稳定性 | 本仓库某次实测 | 公开内容引用值 |
|---|---|---|---|
| **三档计数**（严重/警告/提示） | **完全确定**，任何机器、任何次跑都是同一组数 | 250 / 250 / 220 | 250 / 250 / 220 |
| **耗时** | **随机器与负载浮动**，公开值是一次特定测量的结果 | 0.687s / 1.529s | 0.78s / 1.82s |

也就是说：你复现出的**计数必须**是 250/250/220（对不上就是你环境有问题）；
**耗时大概率对不上公开值**，那是正常的 —— 它取决于 CPU、磁盘和当时系统负载。
关注相对关系（翻倍比）比关注绝对秒数更有意义。

> 公开内容里的 0.78 秒是 15 次独立进程取中位数、范围 0.761–0.882 秒那一次的记录。
> 本仓库 README 表格里的秒数是另一台机器、另一时刻的复现值，两者不同不代表任何一方出错。

## 复现方法

```powershell
# 1) 生成 4000 页合成语料（会清空并重建目标目录）
python build_case.py .\work\case-4000 4000

# 2) 跑体检并计时（独立进程，每档 5 次取中位数）
#    需要 kb.py 来自 https://github.com/TeddyLiu0717/ai-kb-starter
python run_bench.py --kb <kb.py 路径> --out .\work --sizes 1000,4000,8000
```

`run_bench.py` 每次调用都起**独立子进程**计时，原因见下节。

## 为什么用独立进程计时

同一进程内连续调用 `collect()`，首次与后续调用耗时可差 3 倍以上：

| 调用序号 | 1 | 2 | 3 | 4 | 5 | 6-12 |
|---|---|---|---|---|---|---|
| 耗时（秒） | 0.609 | 0.614 | 0.634 | 0.958 | 2.176 | ~2.10 |

同一批文件、同一个结果（4000 页 / 720 条问题），差异来自文件句柄缓存与 OS 页缓存状态，
不是算法复杂度变化。用户实际是每次敲一条命令，所以独立进程计时更接近真实体感。

## 交叉校验

`build_case.py` 里另有一份**独立重写**的判定逻辑（`expected_counts`），
不调用 `kb.py` 自己算，严重/警告/提示三项必须与 `kb.py doctor` 的真实输出一致。
`run_bench.py` 每档都会做这个比对，结果写入 `bench-result.json` 的 `cross_check_passed`。

## 4000 页用例的缺陷配额（公开内容引用口径）

| 缺陷类型 | 条数 | 判定档位 |
|---|---|---|
| 缺少 YAML frontmatter | 120 | 严重 |
| AUTO 区块缺失 | 40 | 严重 |
| 来源摘要为空或不足 20 字 | 60 | 严重 |
| 断链 `[[不存在的页面]]` | 30 | 严重 |
| 核心观点少于 3 条 | 50 | 警告 |
| concept 页面 sources 为空 | 60 | 警告 |
| type 不在约定范围 | 40 | 警告 |
| frontmatter 缺少字段 created | 50 | 警告 |
| 未在 wiki/index.md 注册 | 100 | 提示 |

合计：严重 250 / 警告 250 / 提示 220，`kb.py doctor` 退出码 1（未通过质量门）。

缺陷注入到互不重叠的页面集合，因此三类计数可以直接相加对账。
